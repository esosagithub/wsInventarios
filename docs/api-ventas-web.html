v2.0 https://ns.aseyco.com:444/picking

Introducción

Esta API permite registrar ventas con estructura cabecera-detalle en el esquema Oracle pedidos_web_vtex. Cada llamada a POST /ventas persiste la cabecera en ventas_web, las líneas de productos en ventas_web_detalle y los medios de pago en ventas_web_pagos, todo dentro de una única transacción atómica. También permite consultar pedidos pendientes, marcarlos como procesados, consultar stock y consultar precios. Todas las solicitudes y respuestas se realizan en formato JSON. La autenticación se implementa mediante JWT Bearer Token.

URL Base:  https://ns.aseyco.com:444/picking/vtex
Importante: Todas las solicitudes deben incluir el header Content-Type: application/json. Los endpoints protegidos requieren además Authorization: Bearer {access_token}.

Autenticación

La API utiliza un sistema de dos tokens JWT para gestionar la sesión de forma segura.

access_token
Duración: 4 minutos
Se envía en el header Authorization: Bearer de cada solicitud protegida. Debe renovarse cuando expira.
refresh_token
Duración: 5 minutos
Se usa únicamente en el endpoint POST /refresh para obtener un nuevo par de tokens sin re-login.

Campos de la Venta

Referencia completa de todos los campos aceptados en POST /ventas, organizados por sección del JSON.

Estructura vigente: cada campo se inserta exactamente como llega en el JSON; no se interpreta dato1-dato20 como sustituto de otros campos. La cabecera acepta fac_total, fac_subtotal, fac_iva, fac_descuento, campos codificados de entrega cliente_departamen_code/name, cliente_provincia_code/name, cliente_distri_code/name, campos de pickup pickup_name/type/document/number y campos de facturación fac_cliente_*, fac_departamen_*, fac_provincia_*, fac_distri_*. En detalle[] acepta unidad_medida, promotion_code, promotion_type, promotion_group. En pagos[] acepta subtotal_tc, iva_tc y paymetodo.

Flujo de Integración

Pasos recomendados para integrar la API en la aplicación cliente.

1
Autenticación inicial
Al iniciar sesión, llamar a POST /picking/vtex/login con las credenciales. Guardar el access_token y el refresh_token en memoria de la aplicación.
2
Enviar solicitudes autenticadas
En cada request al endpoint protegido, incluir el header:
Authorization: Bearer {access_token}
3
Detectar token expirado
Si la respuesta es 401 con code: "TOKEN_EXPIRED", el access_token venció. Proceder a renovarlo (paso 4).
4
Renovar el token automáticamente
Llamar a POST /picking/vtex/refresh con el refresh_token. Si es exitoso, guardar los nuevos tokens y reintentar el request original.
5
Manejar sesión expirada
Si /refresh devuelve REFRESH_EXPIRED, la sesión expiró completamente. Redirigir al usuario al login para iniciar desde el paso 1.
Pseudocódigo — lógica de reintento recomendada
Pseudocódigo
